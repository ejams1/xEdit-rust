# xEdit-rust
Rebuild of the xEdit project in Rust. Additionally features CLI control of all xEdit features and native support for AI agents to control it.

The build plan is in [docs/PLAN.md](docs/PLAN.md).

## Goals

- Port xEdit to Rust with 1:1 functionality*
  - Morrowind and Enderal are loaded but not verified against the oracle yet (it can not dump or save Morrowind plugins, and Enderal is not installed); verified support comes later
- Match the upstream release build exactly
  - The official binaries of the baseline tag (`xedit-4.1.5q`) are the oracle; a differential harness compares the port's output with theirs on the real game files, and each phase closes only when its parity gate holds. Upstream quirks are reproduced, not corrected.
- Keep existing scripts, plugins and workflows working. Compatibility with xEdit behaviour, its Pascal scripts and the files it writes wins over every other concern.
- Be easier to contribute to than the Delphi original: a modern toolchain (`cargo build`, `cargo test`, clippy, one command for the parity check), no proprietary compiler, typed interfaces instead of 103 COM-style interfaces in one 50,000-line unit, and a module per upstream unit so the Pascal source stays a readable map of the Rust.
- Expose every operation through the `xedit` CLI as a typed command with `--json` output, stable error codes and a printable schema (`xedit schema`), so that an AI agent can discover and drive the whole tool without the GUI.
  - Make mutation safe for agents: an explicit edit flag, `--dry-run`, structured outcomes, atomic saves with a backup, and a long-lived session (`xedit batch`, `xedit serve`, `xedit mcp`) that runs the same commands.
- Stay mergeable with upstream. One Rust module per Pascal unit with matching names, and `upstream-map.toml` records the last upstream commit merged into each, so upstream changes map onto the port line by line.
- Get faster than upstream once parity holds

## Non-goals

- No new file formats, record definitions or game support beyond what the baseline tag ships. New upstream releases are taken in through the sync procedure, not ahead of it.
- No redesign of the data model, the scripting language or the GUI. JvInterpreter Pascal stays the script language; the GUI reproduces the upstream forms on top of the same commands.
- No separate agent API. Agents use the same command layer as the CLI and the GUI; there is no second surface to keep in step.
- No dependence on a Delphi compiler. The oracle is the released binary, never a rebuild.
- No non-Windows platform before the Windows port is complete. Linux and macOS follow, behind thin platform modules.
- No game files in the repository. The parity corpus comes from local installs through environment variables.

## Status

- Phases 0 to 2 of the plan are done: every game mode from Morrowind to Starfield and every save format load and dump like the release build, verified file by file against it on the local game installs (Morrowind's masters and Enderal are not verified: the oracle cannot dump Morrowind plugins and Enderal is not installed on the development machine).
- Phase 3 (write path and daemon) is done on draft pull request #12. A loaded plugin can be edited, saved and served to a long-running session, and the saved bytes are xEdit's. `cargo xtask parity oracle-save` drives the xEdit GUI release build headlessly to save every plugin of the corpus and compares the port's save with it: 239 of 249 plugins are byte-identical, 7 are refused with the same message by both, and the 3 Morrowind masters have no oracle save because the 4.1.5q GUI cannot save Morrowind plugins; `cargo xtask parity roundtrip` loads and saves the corpus and agrees. `cargo xtask parity oracle-edit` replays scripted edit sequences on both: the 4 of phase 3 give the oracle's bytes since phase 4 (the master update of a plugin with unchanged sorted arrays differed at the end of phase 3).
- The write commands are `xedit elements set|add|remove` (any element by path, a member, an array entry or a child record such as a reference of a cell), `xedit records copy|delete` (as an override or a new record, deep, with the masters it needs added), `xedit masters add|sort|clean` (with every FormID of the plugin rewritten to follow them), `xedit formids change|renumber` (updating the records that refer to the changed FormIDs), `xedit files flags` (ESM, ESL, medium, update, blueprint, localized) and `xedit save`. Every mutating command takes `--dry-run`, refuses to run without the global `--edit` flag otherwise, and changes memory only until `xedit save`. The AfterSet and AfterLoad callbacks of the definitions run, as in xEdit.
- `xedit batch` runs several commands in one session, so an edit and its save go together. `xedit serve` keeps a session loaded and answers every registry command as a JSON-RPC method over stdio or a Windows named pipe, and `xedit mcp` serves the same commands as MCP tools over stdio; both are built from the registry at run time, keep the `--edit` gate and `dry_run`, and leave saving to an explicit `files.save`. The skills `using-xedit-cli` and `adding-a-command` under `.claude/skills` describe how to drive the tool safely and how to add a command.
- Loading reads the groups of a plugin on all CPUs and `xedit dump` builds and writes the records on all CPUs (`--threads N`; about five times faster on `Skyrim.esm` than on one thread), with output that does not depend on the thread count.
- Known gaps of the write path, all listed in [docs/PLAN.md](docs/PLAN.md) under "Owed from phase 3": copying over an existing override and partial forms, the order of the responses of a topic after a master update in the games that sort them by their `PNAM`, the identity FormID of a Morrowind record, and one session per process.
- Phase 4 (analysis and tool modes) is in progress on draft pull request #13. Conflict detection is done: `xedit conflicts` gives the conflict status of every record of the loaded plugins as xEdit colours it (master, override, identical to master, conflict winner and loser, critical conflicts of injected records, game settings compared by editor ID), with per-file counts and filters, and `xedit compare` shows the records of a FormID side by side, row by row, as the view tab does. `cargo xtask parity conflicts` has the xEdit GUI classify every record of the vanilla plugins of each game and compares: 23.4 million records of 10 games equal (Morrowind has no oracle: the GUI runs it in view mode only). The comparison runs on all CPUs with the same output for every thread count. A session now reads plugins with the editor's settings (simple records, hidden unused fields, the contained-in elements, the sorted responses of a topic), as xEdit does; `xedit dump` keeps xDump's. The reference index is done: `xedit refs get` lists the records that refer to a record (xEdit's "Referenced By" tab) and the records it refers to, `xedit refs build` builds the index of the loaded files on all CPUs or loads it from xEdit's reference cache files, which the CLI reads and writes in xEdit's format, and edits keep it right; `formids change|renumber` use it. `cargo xtask parity refs` has the xEdit GUI build the index of the vanilla plugins of each game and compares every referenced-by list and every cache file: 33.2 million entries of 5.8 million records of 9 games equal, built and loaded from the cache, with every cache file of those games equal after decompression; Starfield differs in 18 entries, from perk activities whose JSON the port does not read yet.
- Error checks are done (phase 4 step 3): `xedit check` is xEdit's "Check for Errors" (`mniNavCheckForErrorsClick`, the registry's `files.check`): it loads the plugins with that mode's settings and checks the records on all CPUs, printing what xEdit's message log prints (the record, the `element -> error` of every error, `Above errors were found in:` after the elements of a container with errors), and `--json` gives the records and their errors; `xedit dump --check` is xDump's `-check`. `cargo xtask parity check` runs the xEdit GUI's own check mode on the vanilla plugins of every game and compares the log lines, the counts and the exit code: 246 of the 249 plugins equal (one of them, a Fallout 76 file, has an oracle log that lost lines under load, with every line it kept and the counts equal), and the 3 Morrowind masters have no oracle (the GUI runs the game in view mode only); `cargo xtask parity check-dump` compares xDump's `-check` with `xedit dump --check` over the same corpus, the files whose dump the oracle crashes on compared as prefixes.
- Plugin cleaning is done (phase 4 step 5): `xedit clean --quick` is xEdit's quick auto clean mode (undelete and disable the deleted references, remove the records identical to their master, save, repeat), loading the plugins with that mode's settings as xEdit does, and `--itm`, `--udr` and `--dry-run` run the steps alone or count them; `xedit records cleanup-injected` is "Cleanup injected records". `cargo xtask parity clean` runs xEdit's own quick auto clean mode headlessly on every corpus plugin that has masters and compares the saved bytes, the counts and the cleaned records with the port's (results in [docs/PLAN.md](docs/PLAN.md)).
- Mod groups are done (phase 4 step 6): `xedit modgroups list|show|select|create|edit|delete|update-crcs` reads and writes xEdit's `.modgroups` files and its saved selection as xEdit does, and `xedit conflicts --modgroups NAME`, `--all-modgroups` or `--saved-modgroups` leaves the records the active groups hide out of the comparison (`ctHiddenByModGroup`). `cargo xtask parity modgroups` has the xEdit GUI activate, edit, delete and update mod groups from its menus, answering its dialogs headlessly, and compares the conflict status of every record, the files it writes and its validation messages: 9 of 9 scenarios on Skyrim SE and Fallout 4 equal.
- Localization is done (phase 4 step 7): a localized string of a localized plugin can be set and copied (the text goes into the plugin's string tables, a new string takes the next free ID), `xedit save` writes the changed `.STRINGS`, `.DLSTRINGS` and `.ILSTRINGS` tables next to the plugin as xEdit writes them, `xedit localization localize|delocalize` is xEdit's "Localize plugin" (with its translation from other tables) and "Delocalize plugin", and `xedit localization files|strings|get|set|export|languages|language` are the localization editor and the Language menu; `--language` picks the tables' language and `--translate` loads in xEdit's translate mode. `cargo xtask parity oracle-edit` gives the xEdit GUI the game's string tables, has it save its own tables and compares them: the edits, localizations and delocalizations of Skyrim SE, Fallout 4 and Starfield plugins give xEdit's bytes for 26 of 27 saved plugins and tables (results in [docs/PLAN.md](docs/PLAN.md)).
- Merged patches are done (phase 4 step 8): `xedit patch merged <name> [--dry-run] [--no-save] [--output] [--no-backup]` is xEdit's "Create Merged Patch" — the leveled lists, containers, faction relations, races, form lists (the ordered form lists whose editor ID ends in `OrderedList` take appends only, and a faulty one is reported and left out), actor items, factions, effects, perks and keywords, and the keywords of the items and effects of the newer games, merged into one new plugin so that no plugin's changes are lost to the one that loads last; `xedit files new` is its `AddNewFile`. `cargo xtask parity merged` makes the scenario's plugins with the port, has the xEdit GUI create its merged patch with the same files (clicking the menu items that activate mod groups and answering its dialogs headlessly) and compares the patches byte for byte: 12 of 12 scenarios on Fallout New Vegas, Skyrim SE, Fallout 4 and Oblivion equal, the faulty ordered list's message included (results in [docs/PLAN.md](docs/PLAN.md)).
- The filter of the navigation tree is done (phase 4 step 4): `xedit filter apply` runs every option of xEdit's filter dialog over the loaded plugins and reports what it keeps (the two passes, the nodes left and the records taken out of each file), either from the options in the request or from a `[Filter <name>]` preset of xEdit's settings file, which `xedit filter presets|save|delete` manage; `xedit filter remove` takes the filter off, and `xedit refs build-reachable` is "Build Reachable Info", which the not-reachable option reads. The view filter of the view tab is the `--view-filter-name|value` options (with `--keep-children`, `--keep-siblings`, `--keep-parents-siblings`) of `xedit compare`, and the referenced-by filter is the `--filter-name|signature|file` options of `xedit refs get`. `cargo xtask parity filter` has the xEdit GUI apply filters from its script API and compares the counts it logs (results in [docs/PLAN.md](docs/PLAN.md)).
- Tool modes are done (phase 4 step 9): `xedit tool modes` lists the seventeen modes of `xeInit.pas` with the switch of each, and `xedit tool run <mode>` runs one over the loaded plugins — `setesm`, `clearesm`, `masterupdate`, `masterrestore`, `onamupdate`, `sortandcleanmasters`, `generateseq` (the `.seq` files of the start-game-enabled quests a plugin adds), `checkforerrors`, `checkforitm`, `checkfordr` (which count and exit with the count, at most 127, as xEdit does) and `export` (xDump's `-export RAW`: the profile of the game's record definitions, written as a file and printed as the structure of the definitions). Each mode loads with the settings `xeInit.pas` gives it (the internal edits, the reference information, the translate mode, the ONAM filter and the rest). The command line of xEdit itself is read too: `parse_legacy` (the port of `wbCommandLine`'s `wbFindCmdLineParam` and of `DetectAppMode`) accepts the switches a mod manager passes — `-quickautoclean -qac -quickclean -checkforitm -checkfordr -CheckForErrors -translate -setesm -clearesm -masterupdate -masterrestore -onamupdate -sortandcleanmasters -generateseq -export -lodgen -script -D: -P: -l: -autoexit -autoload -IKnowWhatImDoing` and the rest, including the executable names (`SSEEditQuickAutoClean.exe`) and the game switches (`-SSE`). `cargo xtask parity tool-modes` has the xEdit GUI run each mode it has on the corpus plugins and compares the saved bytes, the message log lines and the exit codes (results in [docs/PLAN.md](docs/PLAN.md)); `-CheckForErrors` is `parity check`, `-dump` is `parity dump` and `-quickautoclean` is `parity clean`.
- The phase-4 agent workflow skills are under `.claude/skills`: `auditing-conflicts` (which override of a FormID wins and what the conflict statuses mean, narrowing the list to the records a plugin wins or loses, the side-by-side compare of a record, the mod groups that hide records and the reference index that shows what a record is used by), `cleaning-plugins` (the ITM and UDR steps, the quick auto clean mode and the injection cleanup, with what the oracle check showed) and `building-patches` (xEdit's merged patch and purpose-built override patches made from `files new` and `records copy`). They are the native replacements for the `xEdit-llm` daemon's comparison, cleaning and patch routes.
- Phase 4 (analysis and tool modes) is done and its gate is met: the conflict status of the vanilla plugins of 10 games (23,383,514 records) equals the oracle, so does the reference index of 9 games (5,829,130 records with 33,228,829 entries, every cache file equal after decompression; Starfield is short by the 18 entries of the perk activities whose JSON the port does not read), the cleaning result of 231 of 238 corpus plugins (every pass's counts and every cleaned record line the oracle's; the 4 files that differ do so in the bytes of records the clean did not touch) and the error check output of 245 of 249 plugins (and, through xDump, 246 of 246 files). The phase's other oracle checks are in as well: the filter (37 of 37 and 8 of 8 configurations and the reachable-information scenario, results and what is owed in [docs/PLAN.md](docs/PLAN.md) under phase 4), 9 of 9 mod group scenarios, 12 of 12 merged-patch scenarios, the localization sequences (26 of 27 saved plugins and tables in the ten step-7 sequences, 31 of 32 saved files over all 15 since step 8, the one difference the known Starfield delocalize emulation limit) and 24 of 31 tool-mode cases (4 `known-difference` in the export, 3 `oracle-unsupported`). What is still owed, with the numbers, is in [docs/PLAN.md](docs/PLAN.md) under phase 4.
- Archives (phase 5 step 1): `xedit archive list|extract|pack` and the `bsarch` binary read, unpack and write BSA (Morrowind, Oblivion, Fallout 3, New Vegas, Skyrim LE and SE) and general BA2 (Fallout 4, Fallout 76, Starfield) archives. `bsarch` takes the arguments of `BSArch.exe` and prints its text. Packing runs on all CPUs, and the archives are byte for byte the ones `BSArch.exe -mt:no` writes, for every thread count: `cargo xtask parity bsarch` compares the listings, the unpacked files and the packed archives of the game archives with the oracle. The texture archives (`DX10`, Fallout 4 and Starfield) pack and unpack too (phase 5 step 2): a DDS file is stored as chunks of mipmaps and written again with the header xEdit makes, byte for byte as `BSArch.exe` does for the 125 texture archives of the corpus and for generated DDS folders, with the pixel conversion and the half-float array conversions on vector instructions where the machine has them (a scalar version gives the same bytes; `XEDIT_SIMD=off` forces it).
- NIF meshes and materials (phase 5 step 3): `xedit assets dump|blocks|save|set|from-json` read, dump, edit and write the NIF and KF files of every game from Morrowind to Fallout 4, Fallout 4 BGSM and BGEM materials, the LOD settings and tree LOD files, FUZ voice files and DDS headers, loose or inside an archive. A file loaded and saved gives xEdit's bytes, and the dump is the JSON of Sniff's converter or xEdit's text dump: `cargo xtask parity nif` compares the port with `Sniff.exe` and with the xEdit GUI's script adapter on every mesh and material of the game archives. Fallout 76 and Starfield meshes are refused with xEdit's own message, as the 4.1.5q release does; optimizing and stripifying a mesh is the Sniff operation `Optimize mesh` (step 6), the `SpellOptimize`, `SpellStripify` and `SpellTriangulate` functions themselves having no command of their own.
- Sniff (phase 5 steps 4 and 5): `xedit sniff list|run` and the `sniff` binary (which takes the arguments of `Sniff.exe`'s automation mode) run 49 of Sniff's 50 batch operations on the meshes, animations and textures of a folder or an archive, on all CPUs: updating tangents and bounds, applying and adjusting transforms, the universal tweaker and fixer, the JSON converter, replacing asset paths, copying and merging geometry and shapes, painting vertex colours, copying and adding animation blocks (headtracking, facial, transform data, controlled blocks, skeleton bones), the Havok, shader flag and animation operations, optimizing and analysing meshes, and the reports (check for errors over meshes and textures, find textures, draw calls, UVs, transforms, Havok info). `cargo xtask parity sniff` compares each operation's output files and log with `Sniff.exe` on the game archives, the texture operations on the DDS files of the texture archives and of the unpacked samples of the others. `Update MOPP code` stays unported (it calls `NifMopp.dll`, a Havok library the port does not have) and `ProcCollapseLinksArrays` is not registered in the 4.1.5q form.
- LOD generation (phase 5 step 6): `xedit lodgen` runs xEdit's LODGen mode on the loaded plugins, Oblivion's distant LOD (`.lod` and `.cmp`), the trees LOD (billboards, `.lst` list, `.btt` and `.dtl` blocks, the atlas and its split) and the objects LOD of Skyrim and the Fallouts, with the form's options (`--set`, the settings file), a recoverable tree-rotation seed and the export files `LODGenx64.exe` consumes. `cargo xtask parity lodgen` compares every output file, export file and log line with the GUI's LODGen mode: 20 of 20 cases equal (Fallout 4, Skyrim SE, New Vegas, Fallout 3 and Oblivion worldspaces, the atlas formats and sizes, trees LOD with billboards and with 3D trees, the splits of the atlases).
- Phase 5 (archives, assets and LOD) is done and its gate is met: packed archives are byte-identical to `BSArch.exe -mt:no` (`cargo xtask parity bsarch`: 1553 of 1553 checks equal, 0 different, over the archives of the 11 games and the synthetic folders), and the Sniff and LODGen outputs equal the oracle (`cargo xtask parity nif`: 542505 files equal, 0 different; `cargo xtask parity sniff`: every case run on the full corpus equal, the per-case numbers and the cases still owed in [docs/PLAN.md](docs/PLAN.md); `cargo xtask parity lodgen`: 20 of 20 cases equal). The skills `handling-archives` and `nif-batch-operations` under `.claude/skills` describe the asset commands.
- Later phases (scripting, GUI, performance, release) have not started; phase 5 is done, its skills and docs step included, and phase 4 is done and its gate is met, pending its merge into main.
