# Writing xEdit scripts

The port runs xEdit's Pascal scripts with a JvInterpreter-compatible interpreter (`crates/xedit-script`), driven by the port of `xeMainForm.pas`'s `DoRunScript`/`ApplyScript` (`crates/xedit-session/src/script.rs`). The compatibility goal is the phase-6 gate: the 150 shipped `.pas` scripts of the 4.1.5q `Edit Scripts` folder parse (150 of 150), every form-free script that runs produces the oracle's output, and the language probes of `cargo xtask parity script --phase probe` (`crates/xtask/oracle/scripts/probes/`, 880 small scripts run on both sides over a probe master) agree with the oracle (880 of 880, with `probes.json` accepting the 32 faults, hangs and documented divergences with reasons). This skill says when to reach for a script, how to run one, and what the port does and does not answer.

## Script or `xedit batch`?

Use `xedit batch` (see the `using-xedit-cli` skill) when the work is a list of commands you can name up front: a few `elements set`, `records copy`, `masters add`, then `save`. Use a script when the logic depends on the data:

- Walk every record of a load order and decide per record (filtering, checking, renaming with a condition, collecting totals).
- Keep state across records or recurse (`Initialize` state, `Finalize` writing a report; `Check for errors.pas` recurses the element tree).
- Write report or data files in a format you control (`wbOutputPath`).
- Run an existing script unchanged. The corpus scripts (and mod authors' scripts) are the compatibility surface; prefer running one over rewriting it as commands. `xedit script list` names the folder's scripts, and `XEDIT_SCRIPTS` points it at another folder.

A script is also the only way to exercise the script API itself, but it is not always the safer tool: a script that builds or shows a form cannot run headless (see "Headless and the Vcl seam"), and a script's failure saves nothing only when it aborts before its `SaveChanged` at the end. For a quick, reviewable change, commands are easier to dry-run and read back.

## Running one

```
xedit script list [--scripts DIR]                       # script.list, read-only
xedit script check MyScript.pas [--json]                # script.check, read-only
xedit --edit --game sse --load "<Data>\Update.esm" \
      script run MyScript.pas [--scripts DIR] [--dry-run] [--no-save] [--build-refs]
```

- `script list` lists the `*.pas` of the scripts folder (the top folder only) with line counts, as the form's list shows them. The folder is `--scripts`, else `XEDIT_SCRIPTS`, else the oracle's `Edit Scripts` (`XEDIT_ORACLE_DIR`), else `Edit Scripts` beside `xedit.exe` — upstream's `wbScriptsPath`, which `-S:` sets.
- `script check <file>...` compiles each script and the units it `uses`, exactly as `TJvInterpreterUnit.Compile` accepts them: a routine body is only scanned for its balanced `end`, so a statement-level error inside a body surfaces when the script runs, not here. It exits 0 when all compile, else non-zero listing each failure as `file:line: message` (with `--json`, the structured result). A unit with no file beside the script is a unit compiled into the host and parses to nothing.
- `script run <file>` is xEdit's `-script:` mode: the script compiles, `Initialize` runs, `Process` runs per selected element, `Finalize` runs, then every plugin the run changed is saved (the GUI's `SaveChanged` on close): the port writes the file in place at once and logs the GUI's lines (`Saving: <name>.save.<timestamp>`, `Queued renaming of save ... on shutdown.`, `Done saving.`), without the GUI's backup folder. A relative file name resolves against the scripts folder, but the units a script `uses` always resolve from the script's own folder, as `DoRunScript` sets `wbScriptsPath`.
- `--dry-run` runs the script with editing disabled and saves nothing; `--no-save` leaves the changed plugins in memory, for `xedit save` in the same `batch` or `serve` session. A one-shot run with `--no-save` and no save afterwards loses the changes. `--build-refs` builds the reference information before the script runs, as the GUI's script mode does at its load (`-nobuildrefs` turns it off there): the scripts that read `ReferencedBy` need it; off by default. Needs `--edit` unless `--dry-run` (registry gate, as every mutating command); `script list` and `script check` need no `--game` or `--load`.
- Exit status: `script check` exits non-zero when a script does not compile; `script run` exits non-zero when the script aborted. With `--json` the run response has `file`, `script`, `dry_run`, `processed` (the `Process` calls that returned), `aborted`, `self_terminated`, `error`, `error_location`, `files` (changed/saved) and `messages` (the run log). `xedit schema` (or `call script.run --params '<json>'`) is the authority on fields; `save` is true by default on the registry request, so `--no-save` is `"save": false` through `call`/`batch`.
- The `-script:<file>` legacy switch and `xedit tool run script --script <file> [--scripts DIR]` run the same path and save as the auto modes do.
- A run needs no selection option: headless, `DoRunScript` selects every root node of the navigation tree, so `Process` sees every loaded file's elements from the last back to the file node (a file's records in the reverse of their order, the file node last). The script narrows this in `Initialize`: `ScriptProcessElements` (default `[etMainRecord]`; `[etFile]` selects the file nodes) and `ScriptProcessSignatures` (a comma-separated list of 4-character signatures, upper-cased and matched as a substring).

A safe sequence, dry run first, then save somewhere else through `batch`:

```
xedit --game sse --load "<Data>\Update.esm" script run MyScript.pas --scripts <scripts> --dry-run
xedit --json --edit --game sse --load "<Data>\Update.esm" batch - <<'JSON'
[
  {"command": "script.run", "params": {"file": "MyScript.pas", "scripts": "<scripts>", "save": false}},
  {"command": "files.save", "params": {"file": "Update.esm", "output": "<scratch>\\Update.esm"}}
]
JSON
```

## Where the API lives

- **`xEditAPI.pas`** in the oracle's `Edit Scripts` is the declaration reference: 1,633 lines declaring 202 routines, the `IInterface` element type and the constants a script compiles against. An agent writing a script should read the declarations there for signatures. At run time the host stubs `xEditAPI` (as upstream does), so `uses xEditAPI` resolves to the host's registrations; the port's `script check` parses the real file when the folder holds one, because that file is part of the corpus gate.
- **`coverage/ledger.toml` is the source of truth for the ported surface.** Every registration is a `[script."<Unit>:<Class>.<Member>:<kind>"]` entry (`kind` is `function`, `const`, `get`, `set`, `iget`, `iset`, `idget`, `idset`, `class`, `rec`, `recget`, `recset`, `handler`, `extfun` or `extunit`) with `status = "covered"` (and `command = "script.run"`), `"presentation"`, `"excluded"`, or `"pending"`. After parity #26's VCL reclassification (parity #38 in): 3,663 entries — 3,552 covered, 54 presentation (the `TCanvas` members and the paint methods a renderer draws), 30 excluded (the registrations commented out upstream), 27 pending. The 27 pending are 26 functions of `xejviScriptAdapterHost.pas` (`AddNewFile`/`AddNewFileName`, `JumpTo`, `RecordByHexFormID`/`RecordFromFileByFormID`, `FileByLoadOrder`/`FileByLoadOrderFileID`, `wbSelectedFiles`/`wbSelectedFilesToFileNames`, `wbSettings`/`wbSettingsFileName`, `wbSimpleRecords`, `wbRecordDefMap`, `wbLoadBSAs`, `wbTrackAllEditorID`, `IsPositionChanged`, `ExecuteCaptureConsoleOutput`, the conflict helpers `ConflictAllForElements`/`ConflictAllForNode`/`ConflictThisForNode`, the LOD and atlas builders `GenerateLODTES4`/`GenerateLODTES5Objects`/`GenerateLODTES5Trees`/`wbDecodeTextureHashes`/`wbGetUVRangeTexturesList`, and the form handles `frmMain`/`frmFileSelect`) and one `JvInterpreter` entry; `wbBuildAtlasFromAtlasMap` and `wbBuildAtlasFromTexturesList` are bound since parity #38 (the `atlas` probe). A script that calls a pending name aborts with `Undeclared Identifier '<name>'`. `excluded` is used for registrations commented out upstream; the VCL members are the headless object model's since parity #26, and only the `presentation` members wait for a renderer.
- Check the ledger before promising an agent-written script will run: grep the member name in `coverage/ledger.toml` and read its `status`.

## The dialect

The language is JvInterpreter Pascal — the subset the JvInterpreter interpreter accepts, not full Delphi — and compatibility with the 4.1.5q oracle is the goal; upstream quirks are reproduced, not corrected. What matters when writing a script:

- **The unit shape.** A script is `unit <Name>;` (the unit name matches the file name), with optional `Initialize`, `Process(e: IInterface): Integer` and `Finalize`. A missing routine, or one whose body reads as `begin end` / `begin Result := 0; end` (upstream's `FunctionIsEmpty` source-text scan, six accepted spellings), is skipped. A non-zero `Result` from any of the three stops the run (`Script terminated itself, Result=<n>`) and skips the rest; it is not an abort.
- **Compile is shallow.** `script check` mirrors `Compile`: routine bodies skip to their `end`, so most statement mistakes appear at run time as `Exception in unit <u> line <n>: [<class>] <message>` followed by `Aborted: ...`. `uses` a unit beside the script (`uses Bookmark`, as `Bookmark1.pas` does) and everything in `<scripts folder>\<Unit>.pas` is compiled into the run.
- **The script variables.** `Initialize` may write the filter fields (`FilterByName`, `FilterName`, `FilterConflictAllSet`, `FilterConflictThisSet`, `FilterBySignature`, `FilterSignatures`, ... — the 36 fields of the GUI's filter dialog), then call `ApplyFilter`; `ScriptProcessElements`, `ScriptProcessSignatures`, `wbOutputPath` and `dfFloatDecimalDigits` are the other settable globals. An identifier the host does not know is the interpreter's undeclared identifier, at run time.
- **Registered RTL, not the full language.** `IntToStr`, `Format`, `Pos`, `TStringList`, `TFileStream` and the rest resolve because the JVCL units are registered; a Delphi unit outside the registered set has no members. Indexed properties dispatch through the registered `AddIGet`/`AddISet` pair (`sl[i]`, `sl.Strings[i]`, `el[i]`, `Json.S['x']`), and the default property forms work where the surface registers one.
- **Integer and variant semantics follow the interpreter**: 64-bit `for`/`case` bounds behave as `whatsnew.md` records, `VarType('x')` answers `$102` (`varUString`, the oracle's value), an integer element of a set literal contributes its value (upstream's `SetExpression1` quirk, so build shift-state checks through `ShortCut`), and variant conversions are the interpreter's, with the exceptions in "Known divergences".
- **`Mode:` in the header comment.** `Mode: Silent` is the one keyword upstream reads: it suppresses the run's own log lines, so the closing line alone remains. The CLI `script run` saves changed plugins at the end unless `--no-save`/`--dry-run`, as the GUI's close does.

## Headless and the Vcl seam

Since issue #26 the `Vcl` seam's headless implementation is the VCL object model (`crates/xedit-session/src/script_vcl/interactive.rs`): a script creates real form and control objects (`TForm.Create(nil)`, `TButton.Create(frm)`, `Button.Parent := frm`), reads and writes their properties (`Caption`, `Width`, `Visible`, `ModalResult`, `ItemIndex`, `Checked`, `Items`/`Lines` as the one `TStrings` value; a published property is answered whichever class the JVCL tables registered it on, as upstream's `GetValueRTTI`/`SetValueRTTI` read a control's RTTI before the tables -- `btn.ModalResult` works although the tables carry `ModalResult` for `TCustomForm` alone, and a name that is no published property stays the undeclared identifier), stores event assignments (`Button.OnClick := Handler` -- *stored*, not fired: a real message loop fires them in the GUI phase), and shows a form modal (`frm.ShowModal`) whose answer closes it through the clicked button's `ModalResult`, the VCL's own click rule.

A dialog the script shows is answered from **recorded answers** instead of a window: pass them to `script run` with `--answer '<JSON>'` (repeat, in dialog order) or `--answers <file>` (a JSON array). An answer is `{"class", "title", "keys": [...], "button", "text", "control", "repeat"}` and matches a dialog by its window class and a caption substring -- the same rule the parity harness uses to answer the oracle GUI: `text` goes into the first edit control, `keys` post to the focused control (the arrow keys move a list cursor -- a fresh list selects nothing, so the first Down lands on its first entry -- space toggles a check, return/escape click the default/cancel button) and `button` is clicked by its caption. `control` names the class of the child the text and the keys go to instead (`TCheckListBox`, `TCheckBox`, `TLabeledEdit`), and `repeat` marks an answer that goes to the same form as the one before it: a form with several controls is driven control by control, one answer per control, the last one clicking the button (`Find records.pas` in `runs.json` is the worked example). A file dialog's `text` is the file name; without a drive or a root it is taken under the dialog's `InitialDir`, as the common dialog resolves it. `MessageDlg` returns the `mr*` of the answered button, `InputQuery`/`InputBox` the answered text, `TOpenDialog`/`TSaveDialog.Execute` the file. A dialog with no remaining answer stops the run; the response's `pending_interaction` names the question (`kind`, `class`, `title`, `text`, `buttons`), and `xedit script resume` with the answer appended continues it (the interpreter has no continuation, so the script runs from its start; a deterministic script reaches the same state and proceeds past the interaction). `cargo xtask parity script` drives the same cases on the oracle GUI and on the port (`crates/xtask/oracle/scripts/runs.json`, the `answers` field).

What still refuses: the four `JvInterpreterFm` form-runner functions (`JvInterpreterMakeForm`, `JvInterpreterRunForm`, `JvInterpreterRunFormModal`, `JvInterpreterRunUnit` -- they compile a second unit through a fresh interpreter) and `SelectDirectory` (its own refusal from the misc adapter), with the `[EVclUnavailable]` text below for the former; a VCL unit function the model does not know refuses the same way. Presentational members keep their state and draw nothing headless (the ledger marks the `TCanvas` and paint members `presentation`). The corpus classes 32 of the 150 scripts as `form` and 11 as `interactive` (110 headless), per `crates/xtask/oracle/scripts/corpus.json`; the scripts backed by recorded answers run on both sides (the runs are recorded with pull request #26).

What answers headless, beside everything without a window: the `Windows` value types (`TPoint`/`TRect`, `Point`/`Rect`/`Bounds`, the `TopLeft`/`BottomRight` accessors, the `MB_*`/`VK_*` constants), the `Controls` hint and cursor helpers (`GetShortHint`, `GetLongHint`, `CursorToString`/`StringToCursor`/`CursorToIdent`/`IdentToCursor`), `IsAccel`, `KeysToShiftState`/`KeyDataToShiftState`, the `Menus` shortcut codec (`ShortCut`, `ShortCutToKey`, `ShortCutToText`, `TextToShortCut`, with the key-name table captured from the oracle), the `IniFiles` classes over an in-memory model (`TIniFile` writes through, `TMemIniFile.UpdateFile` writes xEdit's section-per-block text), and `IOUtils`' `TDirectory`/`TFile` (`GetDirectories`/`GetFiles`, `ReadAllText`/`WriteAllText`), and the `Classes` unit's binary streams (`TBinaryReader`, `TBinaryWriter`, `TBytesStream` over the same `TStream` objects as `TMemoryStream`/`TFileStream`, parity #30: `xejviScriptAdapterMiscVcl.pas` registrations bound with the `Classes` unit's stream model, constructors included, and witnessed by the `streams.pas` probe; no corpus script uses them).

## Output conventions

- **Messages.** `AddMessage(text)` appends to xEdit's message log, which is the run's observable output: without `--json` the log lines go to stdout and an abort also writes `error: <location>: <message>` to stderr; with `--json` they are `messages` in the response. Use it for progress and results; a report file goes to `wbOutputPath`.
- **The run log line shapes**, as the oracle's log has them (the `[mm:ss]` prefix is the progress callback's; the text after it is what the harness compares):
  - `[mm:ss] Start: Applying script "<name>"` — dropped for `Mode: Silent`.
  - the script's `AddMessage` lines, each `[mm:ss]`-prefixed.
  - `[mm:ss] Done: Applying script "<name>", Processed Records: <n>, Elapsed Time: <mm:ss>`.
  - `You can close this application now.` — no prefix (it is a plain message log line, `DoRunScript`'s last).
  - per changed plugin `[mm:ss] Saving: <name>.save.<yyyy_mm_dd_hh_nn_ss>`, then `[mm:ss] Queued renaming of save "<data path><name>.save.<time>" to "<data path><name>" on shutdown.`, and a closing `[mm:ss] Done saving.` — after the closing line of a completed run, the last lines of an aborted one.
  - a failure ends the log with `[mm:ss] Exception in unit <u> line <n>: [<class>] <message>` and `[mm:ss] Aborted: Applying script "<name>"`, with no `Done:` and no closing line; the run exits non-zero, and plugins the script changed before the failure are still saved at the end unless `--dry-run`/`--no-save` (a one-shot run stands in for the GUI's close, which saves them too — the harness's aborted save case records the same on the oracle).
- **Files.** A script writes its own files; xEdit's convention is `wbOutputPath` (a trailing separator included), which the port starts as the data folder when nothing set it (`-O:` on the legacy command line sets it) and a script may set itself (`wbOutputPath := 'C:\somewhere\'`). During a run `wbScriptsPath` is the script's own folder and `wbTempPath` the temp folder. xEdit's `cargo xtask parity script` harness captures a run's files by where they were written (`out/` for `wbOutputPath`, `script/` for the run folder, `program/` beside the executable, `data/` for the private data folder), which is a good model for where a script should put things.
- **The filter.** `ApplyFilter` runs when the call that asked for it returns (the run state applies the recorded variables then), so the filter's own log lines appear after the messages of the call that triggered it; `FilterApplied` answers true from the moment it is called, as upstream. With `FilterScripted` on the filter calls the script's `Filter(e: IInterface): Boolean` back through the interpreter, once per main record node its walk reaches (unassigned and 0 are False; a variant that does not convert raises `EVariantTypeCastError`, and a `Filter` that raises aborts the run with `Error during Applying Filter: <message>` then the `Exception in unit ...` and `Aborted:` lines). The flag is read before every record, so a `Filter` that clears it stops the scripted checks there, and the filter clears it when it ends. The `Process` walk after a filter sees the nodes the filter kept alone.

## Upstream quirks a script meets

Behaviour the port reproduces because the oracle has it (parity #23, 2026-10-15; the probes `crates/xtask/oracle/scripts/probes/*.pas` over `tests/fixtures/parity` witness each).

- **Reading a record's name first gives it its required members.** `Name(e)`, `EditorID(e)` or `FullName(e)` on a record that was never looked at runs upstream's quick init. A record whose subrecords all lie before the editor ID and full name members (a `KYWD` without its `CNAM`, an `ACTI` with `EDID` and `OBND` alone) runs the whole init in that quick pass and gains its missing required members as an internal edit, so `ElementCount(e)` counts them afterwards, as it does for a record read through `ElementByName`/`ElementByPath` first. (Upstream then loses every subrecord of that record at its next init; see the divergence below.)
- **The EditorID index after renames.** `RecordByEditorID(file, id)` reads the index (game settings and the other records with `dfIndexEditorID`), which `SetElementEditValues(rec, 'EDID', ...)` keeps current: a record renamed onto a name another record holds is reported (`[<file>] Duplicate Key in Index "EditorID": "<name>" Existing Record: ... New Record: ...`) and not indexed, and the name it left is not taken by that other record; `MainRecordByEditorID(group, id)` searches the group's current names instead.
- **`Copy(s, 0, n)` keeps the count** (`abc` for `Copy('abcdef', 0, 3)`), and `TStringList.DelimitedText` with `StrictDelimiter` splits on the delimiter alone (spaces stay inside the fields).
- **Refused edits raise.** `Add`, `AddElement`, `SetToDefault`, `AddMasterIfMissing`/`AddMasters`/`CleanMasters`/`SortMasters`, `SetIsESM`/`SetIsESL`/`SetIsMedium`, `SetLoadOrderFormID` and `SetIsDeleted` raise upstream's bare `Exception` with the refusal's message (`DefaultImpactDataSet [IPDS:00000276] can not be edited` for a `SetElementEditValues` whose path misses on a hardcoded record, which goes through `Add`), as the value setters already did; the run aborts unless the script handles it, and an `on E: Exception` handler sees the message in `E.Message` and `Exception` in `E.ClassName`.
- **A mid-run move re-visits its record.** The oracle walks the live navigation tree (`vstNav.GetPrevious`), and the tree re-materialises a record's node where the record is now: a record a script moved to another group is reached again when its new place is one the walk has not passed yet, so `Process` runs for it a second time and the closing `Processed Records` count can exceed the file's record count (the issue-#24 fixture `probes/walk-move.pas` pins the second visit of the moved `REFR 0000080A`, and the corpus `Put worldspace references in the right cells.pas` compares equal with its 764,713-line log and saved bytes; `Worldspace displacement.pas` remains the one named case whose count differs, the interruption of its shifts and removals with the re-visits being the batch's recorded owed item). A moved record a later visit processes again shifts its data again, so a script should expect `Process` to see its own edits.
- **A record's name can be stale after a FormID change.** `Name(e)` of a record of an official file is cached (`mrName`/`mrShortName`) and a `SetLoadOrderFormID` does not clear the cache, so the oracle prints the pre-rename `[SIG:FormID]` until a name-relevant subrecord changes (the issue-#24 fixture `probes/topic-renumber.pas` pins it).

## Known divergences

Behaviour a script can meet where the port does not reproduce the oracle exactly. Each is a `known-difference` accepted in `probes.json` (or a `docs/PLAN.md` item); say so rather than guessing when a script trips one.

- **A record read by its name first keeps its subrecords (UPSTREAM-BUG, not reproduced; user decision 2026-10-16).** Upstream's quick init (`GetEditorID` under `mrsQuickInit`, run by `Name`/`EditorID`/`FullName`) of a record whose subrecords all lie before `QuickInitLimit` adds the required members as an internal edit and then releases the elements with the storage invalid; the record's next init collapses the storage from no elements, so the oracle's record has 0 elements, `ElementByName(e, 'EDID - Editor ID')` is nil, and a save writes only what the script adds (`Add Prefix Plus Name To EDID.pas` does this to 850 records of `Skyrim.esm`: 697 `KYWD`, 2 `LCRT`, 69 `AACT`, 82 `ACTI`; the GUI masks it by building the references at load, where every record's first init is a full one). The port collapses the storage from the elements before it releases them (`MainRecordImpl::collapse_storage_after_quick_init`), so the record keeps its data and gains its required members, and the references its `VMAD` or `NAME` holds stay in the index. Witnessed by `probes/edid-quick-init.pas` (the case reads every record through `ElementByName` first, equal) and the unit test `the_quick_init_keeps_the_subrecords_upstream_loses` (the name-first read); `Add Prefix Plus Name To EDID.pas` is a `known-difference` with this reason (`accept` in `runs.json`). Found by the `sse-filters` regression (issue #64), where the loss emptied the `ACTI` whose script properties reference two persistent doors.
- **The string and slot model.** Strings are UTF-8 bytes: `Length('héllo')` is 6 where the oracle counts 5 UTF-16 units, and a `string`/`Char` variable is the one `varUString` kind where upstream's holds a `varString` (`VarType` 256; `Ord(s)` reads the character there). A `string` parameter holds the caller's `varUString` upstream, which cannot be indexed (`aText[i]` raises `Array type required`; copy it into a local variable or use `Copy`), where the port indexes every string (`e-ordidx-*.pas`); `Ord` of a one-character `varUString` is its integer conversion on both sides (`Ord('7')` is 7). A `Cardinal` result is carried as an `Int64` (20 against upstream's `varLongWord` 19), a never-assigned `Double` is the double 0 where upstream holds the `Currency` 0, the custom variant type codes are allocated per kind and not per first use (`sl.ClassType` reads 278 upstream, 279 in the port), and a `TList` item keeps the value's kind where upstream stores the pointer (277). The variant operators themselves are upstream's, including the `'x' + 5` / `'x' + True` `Type mismatch`, and an empty variant (a missing `GetElementNativeValues` path, an unassigned or `Null` variable) compares against an integer as the oracle's does, so an `if` on such a comparison gets its boolean (probes `x-399`, `x-400`).
- **Regex.** `TPerlRegEx` runs the port's own PCRE engine (`crates/xedit-core/src/pcre.rs`, the RTL class in `crates/xedit-core/src/perl_regex.rs`, shared by the script adapter, Sniff's search-and-replace/tweaker and the filter's `CheckValueRegex`): lookaround, in-pattern backreferences, possessive quantifiers and atomic groups, ASCII `\d`/`\w`/`\s` without `PCRE_UCP`, `\Q..\E`, POSIX classes, inline flags, conditionals and PCRE's own compile errors with their offsets, all as the release build answers them. `preNotBOL`/`preNotEOL`/`preNotEmpty` are implemented as `PCRE_NOTBOL`/`NOTEOL`/`NOTEMPTY`, but no script can set them (upstream registers no `State` property either). Not implemented, and a compile error where PCRE compiles the pattern: recursion `(?R)`/`(?1)`, `\N{name}`, `\K` and the `(*VERB)` control verbs; `\p{...}` covers the common properties through Rust's character classes, which is not the same Unicode version as the release's tables. The check is `cargo xtask parity script --script "Regex probe" --phase run`: the probe lives in `crates/xtask/oracle/scripts/probes`, runs over the harness's empty master on both sides and prints offsets and lengths, never a multi-byte text (a value with a byte outside ASCII would depend on the code page the GUI writes its log in).
- **JSON dates and streams (closed by parity #30).** `TJsonBaseObject.LoadFromStream`/`SaveToStream` go through the JVCL `Classes` stream objects, the `UseUtcTime` conversion applies the machine's time zone, `D[]` parses the library's whole date surface and the `jdtUtcDateTime` distinctions are in the model (no registered member creates one: the adapter registers no `UtcDateTime` constant or member). Compared equal by `cargo xtask parity script --phase run --script probes/` over `crates/xtask/oracle/scripts/probes/streams.pas` and `datetime.pas`. What still differs there: the access violation of a nil stream names zero addresses where the GUI prints the faulting ones, a `TBinaryWriter.Write(string)` of a non-ASCII *script* string (a `#233` escape is one byte in the port's byte strings and the character U+00E9 in the GUI's, which its writer encodes as UTF-8), a released stream refuses with `EAccessViolation` where upstream reads freed memory, and a JSON parse error's message: the class and the failure match, but where the library's tokenizer names a token the port's direct parser names its own expectation (the oracle says `Expected "{" but found identifier (1, 2)` for a stream loaded from a position inside the document; `Unexpected end of file where value was expected (1, 9)` is the shape both give).
- **The abort line's class.** A raised data-format error prints `[EJvInterpreterError]` as its class where the GUI prints `[Exception]`. (The `External error in unit ...` wrapper of an earlier tip was removed by the run-parity fixups: a non-interpreter exception prints its bare message with the recorded `unit <unit> line <n>` as the outer location, and an interpreter error's outer location is the cleared `unit  line -1`, both as the oracle prints them.)
- **Runaway recursion and the native stack.** Interpreted calls are guarded at 128 deep and raise the oracle's `[EStackOverflow] Stack overflow` shape; upstream has no guard and dies on its own native stack below 1000 (the oracle runs 100 deep, probes `e-rec-*`), so the guard is a synthetic cap no legitimate script reaches. The expression stack is modelled to upstream's boundary instead: `cJvInterpreterStackMax` holds 199 operands per expression and a flat expression of 202 operands raises `Expression is too complex - overflow` where 201 does not; parentheses, unary operators and a caller's pending arguments each push, as upstream (`e-flat-*`, `e-call-*`, `e-nest-*`). A parse runs on its own 64 MiB thread (nesting cap 1024) where upstream recurses on the native stack.
- **Elapsed time and the save clock.** The origins are upstream's: the `[mm:ss]` prefixes count from the load's start (`wbStartTime`, re-set when `--build-refs` builds the references, `BuildAllRef`) and the `Done:` line's `Elapsed Time` from the `Applying script` action's own start (`PerformLongAction`'s `wbLocalStartTime`) -- the two runs' absolute values still differ by their wall-clock seconds, which the harness strips. The `.save.<timestamp>` suffix is the local clock (`Now`), not UTC; the parity harness still normalizes its digits (the two runs saved seconds apart). The closing line's `Processed Records` segment appears exactly when `Process` ran for at least one element, as upstream.
- **Resources.** `LoadFromResource` reads through the container handler, which a load fills only where a plugin's string tables need the archives, so a resource inside the game archives is not always found (load a localized plugin such as `Skyrim.esm` to have them listed).
- **No-ops and refusals where the GUI exists.** `Free` of a data-format root releases the document (a later call fails with `The file has been freed`; upstream is a use-after-free), `Free` of a non-root does nothing; `O2V(nil)` is `Unassigned`; `MoveUp`/`MoveDown`/`CanMoveUp`/`CanMoveDown`, `InsertElement`, `AssignTemplate*`/`TemplateAssign` and `ElementAssign` run the session commands `elements.move` and `elements.assign` and change the data as the view's Move Up/Move Down and drag and drop do. The element states are the interpreter's own (`SetElementState`/`GetElementState`/`ClearElementState` over `IntToEsState`'s whole range, `esHidden` and the sort keys included, `esDummy` for anything else) and `ContainerStates` answers `TwbContainer`'s mask; `SetEditValue` of a main record runs upstream's gates and, without `wbDisplayLoadOrderFormID`, raises `FormID can only be edited if wbDisplayLoadOrderFormID is active`; `FileWriteToStream` writes the save bytes into a `Classes` stream with the `TwbResetModified` the third argument names. The OS errors are upstream's routes: `TdfElement.LoadFromFile` raises `EOSError` with `RaiseLastOSError`'s text (`System Error.  Code: <n>.` and the system text on the next line), `TdfElement.SaveToFile` `EFCreateError` `Cannot create file "<path>". <system text>`, `TdfElement.LoadFromJSONFile` `EFOpenError` `Cannot open file ...`, and a bare `Exception` reads `[Exception]` in the abort line (not `[EJvInterpreterError]`, which only an interpreter error carries). `SetLength` resizes arrays and strings as upstream does for the element kinds it handles; an `array of string` raises `Array to array assignment` where upstream faults on the raw reallocation (`a-04`), and `SetLength` of a string variable resizes it where upstream's leaves the variable empty (`a-21`).
- **Minor host behaviours (parity #31).** `Beep` is `MessageBeep(0)` (the effect is audible, nothing a script reads); `ShowException` goes through the `Vcl` seam and refuses headless (`[EVclUnavailable] ShowException is not available without a GUI (...)`) where the oracle's modal box ends its run; `DiskFree`/`DiskSize` are the volume API with the JvInterpreter wrapper's `Integer` truncation and the wrapped `Byte` drive argument (`DiskFree(300)` reads the drive 44); `GetLocaleStr`/`GetLocaleChar` read the system's locale (the machine is en-CA, so `GetLocaleStr(0, 31, ...)` is `yyyy-MM-dd`), `GetLocaleChar` answering the first character of values up to four characters and the default beyond that, a NUL for an empty value; `CreateProcessWait` is `CreateProcessW` with upstream's `STARTUPINFO` and `lpApplicationName` (a name without a path resolves against the current directory only, `cmd.exe` fails where a full path runs); `SetRoundMode` reaches the `MXCSR` rounding bits (which the RTL's `Round` and even `0.1 + 0.2` follow) and `SetPrecisionMode` the x87 precision field (no effect on x64 SSE results, as the oracle shows); the default `ShortDateFormat`/`LongTimeFormat`/separators are the locale's (`DateToStr` prints `2026-10-16` on the reference machine, `TimeToStr` `3:07:42 PM` with the locale's own AM/PM strings through the `AMPM` token; the format specifiers are read case-insensitively), while the day and month names stay the port's table. The text-to-number conversions (literals, `StrToFloat`, the variant string reading, the JSON number tokens) run outside the mode `SetRoundMode` sets, as the oracle's do, so `0.1 + 0.2` under `rmDown` adds the nearest `0.1` and `0.2` and rounds the sum down. The float-to-text conversions round in the mode too (fix-numerics: `FloatToDecimal`'s `Power10`, `Round` and division by ten are `MXCSR` operations in the oracle; the port replays each one in the script's mode, so `sys-round.pas` prints digits in all four modes). `ContainerStates` answers 1031 for a container `DoInit`ed and held, 1026 for one read once and reset (`csInitOnce` stays: a record's `EDID`, which the record's own init reads), 1024 for one never read; a main record or a subrecord is held while a script references one of its elements, a value (the record header) while the script references it. Incomplete: `GetLocaleStr` for a value outside ASCII (type 119, the per-mille sign) follows the string model above. `TwbBGSMFile`/`TwbBGEMFile` `ToJSON` and `SaveToJSONFile` raise `Exception` `Not implemented` before they touch the file, as upstream does for materials.
- **Front-end limits.** A routine body terminated by the unit's `.` (`function P: integer; begin end.`) is refused (`';' expected but '.' found`), so two of `FunctionIsEmpty`'s six spellings are unreachable in practice; `xEditAPI.pas` is stubbed at run time even when the folder holds it, as upstream; `-scripthost:` names the script host on the legacy command line (only `JvI` exists; any other value fails with `xeDoInit`'s text). Script and unit files are read as `TStringList.LoadFromFile` reads them (byte order marks, the ANSI code page, CRLF — the line numbers count those line breaks), and the message log is written in the ANSI code page.
- **Numbers.** `StrToFloat` is the RTL's `InternalTextToFloat` (`xedit_core::delphi::str_to_float`, ported from the machine code by fix-numerics, issue #67): the text ends at its first `#0` as a `PChar` does (`'1'#0'.5'` is 1), only spaces are blanks (a tab is refused), the digits go into an unsigned 64-bit accumulator up to `$1999999999999990` and then into a double as `(value * 10 + Ord(ch)) - 48`, the exponent stops reading above 1024 (`1E1000` is `INF`, `1E9999` is refused, `1E-1000` is 0), the scale is the RTL's paired-table `power10` under the default control word whatever `SetRoundMode` set, and a text that is no number may be one of the words `NAN`, `INF`, `+INF`, `-INF` (case-insensitive, as a whole: `Infinity` and `-NaN` are refused); a malformed text or an overflow raises `EConvertError` with `'<text>' is not a valid floating point value`. `FloatToStr`/`FloatToStrF`/`Format` print `FloatToDecimal`'s digits with the RTL's exponent padding (`FloatToStrF(1e22, ffExponent, 17, 0)` is `1.0000000000000000E+22`; `0.1` is `1.0000000000000000E-1`), and those digits round in the mode `SetRoundMode` set (`0.3` prints `2.9999999999999994E-1` under `rmDown`). `FormatFloat` is the RTL's `FloatToTextFmt` (`delphi::float_to_text_fmt`): the digits are `FloatToDecimal`'s rounded half up on the digit string (`FormatFloat('0', 2.5)` is `3`, `FormatFloat('0.00', 0.125)` is `0.13`), a value of 18 or more integer digits without an `E+`/`E-` in the picture is `FloatToStr` (`FormatFloat('0', 1e17)` is `1E17`), the minus sign is written only by the first section, the exponent of a zero is minus the integer placeholders (`FormatFloat('0.00E+00', 0)` is `0.00E-01`) and pads to at most four digits. `SameValue` uses the RTL's `1E-12` resolution; `Round` and `Trunc` keep the low 32 bits of the x64 integer indefinite for NaN and out-of-range values (`Round(NaN)` is 0, `Round(1e19)` is 0), `Ceil`/`Floor` are `Trunc` + `Inc`/`Dec` on `Frac` (`Ceil(1e10+0.5)` is 1410065409), and the `Math` constants are the release's (`MinDouble` the smallest normal, `NaN` `0xFFF8...`). Parity #39 probed all of these (`probes/numerics.pas`, `probes/numerics-parse.pas`). `Frac` of NaN/`INF`/`-INF` is the oracle's `0.0000000000000000E+0`, an upstream quirk the port now reproduces (`Int` of the same values prints `NAN`/`INF`). `dfStrToFloat('NaN')`, `ArcSin(2)` and `ArcCos(-2)` are the RTL's `0xFFF8...` real indefinite (fix-numerics). Owed: `0.0/0.0` raises a division error in the port where the oracle gives NaN (issue #28).
- **Front-end limits.** A routine body terminated by the unit's `.` (`function P: integer; begin end.`) is refused (`';' expected but '.' found`), so two of `FunctionIsEmpty`'s six spellings are unreachable in practice; unit files are read as bytes (no encoding detection); `xEditAPI.pas` is stubbed at run time even when the folder holds it, as upstream; `-scripthost:` is not read (only `JvI` exists).
