# Porting a definition unit

The definition units (`Core/wbDefinitions*.pas` upstream) are thousands of calls to the builder API (`wbRecord`, `wbStruct`, `wbFormIDCk`, ...) plus callbacks written in Pascal. The transpiler `cargo xtask port-defs` translates the builder calls and the simple routines; the callbacks that it cannot translate are ported by hand. Read `porting-pascal-unit` first for the headers, naming and `upstream-map.toml` rules that apply to every unit.

## Layout

- `crates/xedit-defs/src/<unit>.rs` (`common.rs`, `fo4.rs`, `tes5.rs`): generated by the transpiler. Never edit by hand; regenerate.
- `crates/xedit-defs/src/callbacks/<unit>.rs`: the callbacks ported by hand. Common routines go in `callbacks/common.rs` even when only one game calls them; game-specific routines go in the game file.
- `crates/xedit-defs/src/callbacks/<unit>_stubs.rs`: generated stubs for every callback not yet in the hand file. Each panics with `todo!("port <name> from <unit> line <n>")` when called, so a dump that reaches it fails loudly.
- `crates/xedit-defs/src/signatures.rs`: generated signature constants (`cargo xtask port-defs emit-signatures`).
- `crates/xedit-core/src/interface/builders.rs`: the builder API, written by hand with the transpiler's help once. Do not regenerate it with `port-defs emit`: that overwrites the hand-written builders such as `wb_ref_record_record_flags`.

## Regenerating a unit

```
U=<upstream checkout>; D=crates/xedit-defs/src
for u in Common FO4 TES5; do
  l=$(echo $u | tr A-Z a-z)
  cargo run -q -p xtask -- port-defs emit-unit $U wbDefinitions$u $D/$l.rs $D/callbacks/${l}_stubs.rs $D/callbacks/$l.rs
done
```

The last argument is the hand file: every `pub fn` it defines is left out of the stubs. The stub exclusion reads function names from the source text, so define ported callbacks as explicit `pub fn` items, not through macros. The command prints the number of routines translated, the number of stubs written and the number of routines it failed to translate; the failures are listed in the output with their line and are ported by hand like callbacks.

Regenerate every unit after a transpiler change, all fifteen of them: the Common unit decides which routines the game units import, and a name several units declare is named after the unit that resolves (see below). `Common TES3 TES4 FO3 FNV TES5 FO4 FO76 SF1 Reflection TES4Saves FO3Saves FNVSaves TES5Saves FO4Saves` with `$l=$(echo $u | sed 's/\([A-Z]\)/\L\1/g')` is the list; end with `cargo fmt --all` (the emitter writes one long line per statement), and read `git diff` before committing.

## One name in several units

A call or a callback is resolved by the unit it is written in, as Delphi resolves it: the unit's own routine wins, else the copy of the unit it uses last (`add_unit` is given the units in the reverse of the `uses` order, `wbInterface` first). The transpiler keeps the copies apart even when the signatures are equal, so where the copies differ the game's own is what its records name, and the port must provide it:

- The copy of `wbDefinitionsCommon` (or the first unit that declares the name) keeps the base Rust name, which is where the hand file's function lives; a later copy is `<base>_<unit>` (`wbSOUNAfterLoad` of Fallout 3 is `wb_soun_after_load_fo3`, the older `wbLGDIFiltersToStr` of Fallout 76 is `wb_lgdi_filters_to_str_fo76`, `wbOBND` of `wbDefinitionsSF1` is `wb_obnd_sf1` — the last one is generated, not hand-written).
- That name is what the game's generated file references, so a game copy that is not ported appears as a stub in `<game>_stubs.rs`; port it into `callbacks/<game>.rs` under that name.
- `cargo xtask port-defs duplicates <upstream checkout>` lists every routine more than one unit declares with its units, lines and whether the bodies are equal. A copy whose body differs, or that a unit's records name, needs its own port; an equal copy (such as `wbNormalizeToRange` in `wbInterface` against `wbDefinitionsCommon`) is a second hand port so each unit's calls can keep their own name, and both are noted in `upstream-map.toml`.

## Porting a callback

1. Run the dump of a plugin that uses the record type (`xedit dump --game sse <plugin>`); the panic names the stub and the upstream line.
2. Read the Pascal routine. `routines.py <unit.pas> <name>...` in this directory prints the body of a routine by name from the implementation section.
3. Port it into `callbacks/<unit>.rs` with the same name in snake_case (`wbCTDAParam1StringToStr` is `wb_ctda_param1_string_to_str`), the signature the stub declared, and a doc comment `/// Upstream \`<name>\`: <what it does>`. Keep the upstream behaviour including its quirks, marked with `UPSTREAM-QUIRK:` comments. Helpers that upstream shares between callbacks (`wbTryGetContainerFromUnion`, `wbAliasToStr`, `variant_int`) already exist in `callbacks/common.rs`; search before writing one.
4. Regenerate the units so the stub disappears, build, and rerun the dump until it completes.
5. Compare the dump with the oracle (`checking-parity`). A difference in the lines the callback produces means the port is wrong, however reasonable it looks; the oracle is right by definition.
6. Run `cargo fmt`, `cargo clippy --workspace --all-targets`, `cargo test --workspace` and `cargo xtask check`.

Callback types and the Rust signatures the stubs use:

| Upstream type | Rust signature |
|---|---|
| `TwbIntToStrCallback` | `fn(a_int: i64, a_element: ElementArg, a_type: CallbackType) -> String` |
| `TwbStrToIntCallback` | `fn(a_string: &str, a_element: ElementArg) -> i64` |
| `TwbIntOverlayCallback` | `fn(a_int: i64, a_element: ElementArg, a_type: CallbackType) -> i64` |
| `TwbUnionDecider` | `fn(a_base_ptr: DataPtr, a_element: ElementArg) -> i32` |
| `TwbCountCallback` | `fn(a_base_ptr: DataPtr, a_element: ElementArg) -> u32` |
| `TwbDontShowCallback` | `fn(a_element: ElementArg) -> bool` |
| `TwbLinksToCallback` | `fn(a_element: ElementArg) -> Option<ElementRef>` |
| `TwbToStrCallback` (`var aValue`) | `fn(a_value: &mut String, a_base_ptr: DataPtr, a_element: ElementArg, a_type: CallbackType)` |
| `TwbGetConflictPriority` | `fn(a_element: ElementArg, a_conflict_priority: &mut ConflictPriority)` |
| `TwbAfterLoadCallback` | `fn(a_element: &ElementRef)` |
| `TwbAfterSetCallback` | `fn(a_element: &ElementRef, a_old_value: &Variant, a_new_value: &Variant)` |

`ElementArg` is `Option<&ElementRef>`. `a_type` distinguishes `ctToStr`, `ctToSummary`, `ctToSortKey`, `ctToEditValue`, `ctCheck`, `ctEditType`, `ctEditInfo`, `ctLinksTo` as upstream's `TwbCallbackType` does; most callbacks return an empty string for the types they do not handle.

Callbacks that cache per-record data (tint layers, face morphs) keep their cache in a `static Mutex` in the callback file, as upstream keeps a global; the cache key follows upstream exactly.

## Common pitfalls

- A union decider that reads another element of the same record can recurse through the display name of that element. Upstream guards this with `BeginResolve`; the port's `resolve()` guard does the same, so a stack overflow in a dump points at a missing guard, not at the callback.
- `wbIsSkyrim`, `wbIsFallout4` and the other game checks are functions of the game mode, not constants; use the `is_*` functions from `globals`.
- Floats print through `RoundToEx` with the single-precision power of ten and 18 scaled digits (`delphi.rs`); do not format a float in a callback with Rust's formatting. Use `float_to_str_f_fixed` or `format_general`.
- Angles normalize with `TWO_PI`, which is twice the single-precision pi, as upstream.
- `AfterLoad` and `AfterSet` callbacks run on the write path (`AfterLoad` on every load under `wbAllowInternalEdit`, `AfterSet` on every `SetEditValue`), so every one of them is ported; the stub files are empty. The helpers `with_internal_edit`, `set_native`, `set_path_native`, `path_int`, `add_member` and `remove_member` in `callbacks/common.rs` mirror the Pascal idioms (`wbBeginInternalEdit`, `ElementNativeValues[...] :=`, `Add`, `RemoveElement`); bodies that several games share live in `callbacks/common.rs` under a name without the `wb` prefix, and each game's `pub fn wb_...` calls them, because the stub exclusion needs the `pub fn` in the game's own hand file.

## Adding a game unit

1. Add the unit to `upstream-map.toml` with status `in-progress`.
2. Add `define_<game>()` to `crates/xedit-defs/src/lib.rs` and the game to `setup_game` in `crates/xedit-session/src/dump.rs` (game name, executable name, master name, encodings of the string tables).
3. Run the transpiler for the unit, then dump each vanilla plugin of the game and port the callbacks it hits.
4. Produce the oracle dumps with `xDump.exe` (`checking-parity`) and compare every vanilla plugin byte for byte.

## The data format units

`wbDataFormatNifTypes` and `wbDataFormatNif` (NIF blocks, phase 5 step 3) declare their definitions with the builder functions of `wbDataFormat` (`dfStruct`, `dfArray`, `dfUnion`, ...), not with `wbRecord`. Their transpiler is `cargo xtask port-defs emit-df` (`crates/xtask/src/portdefs/df.rs`), which uses the same Pascal reader:

```
U=<upstream checkout>; A=crates/xedit-assets/src
cargo run -q -p xtask -- port-defs emit-df $U wbDataFormatNifTypes $A/data_format_nif_types/defs.rs $A/data_format_nif_types/stubs.rs "$A/data_format_nif_types/callbacks.rs;$A/data_format_nif_types.rs"
cargo run -q -p xtask -- port-defs emit-df $U wbDataFormatNif $A/data_format_nif/defs.rs $A/data_format_nif/stubs.rs "$A/data_format_nif/callbacks.rs;$A/data_format_nif.rs"
cargo fmt
```

- Every overload of a builder becomes a function of its own: the one with the most parameters keeps the base name (`wb_vector3`), the others get their parameter names (`wb_vector3_name_events`, `wb_vector3_name`). The overloads of the `df*` functions are completed to their full form at the call (`dfFloat('X')` is `df_float("X", DataType::Float32, "", &[])`), with upstream's quirk that `dfBool(name, type, events)` drops the events.
- `wbDefine*` procedures take the registry (`infos: &mut NiObjectInfos`); the version variables `v4002` to `v20207` are the constants `V4002` to `V20207` of `data_format_nif.rs`.
- Callbacks (any routine whose first parameter is a `TdfElement`) are translated when they stay in a small typed subset: `nif(e).Version` and the user versions, `with nif(e) do`, `NativeValues`/`EditValues`/`Elements[...]` lookups and assignments, comparisons of variants with integers, `in [...]`, `and`/`or`/`not`, local variables, `if`, `for`, `Inc`/`Dec` and `Exit`. The rest are ported by hand in `callbacks.rs` (a `pub fn` there, or in the parent module named after the hand files, is never generated) and are stubbed until then: the stub returns the error `not ported: <name> line <n>`, so a load that reaches it fails with the name. The generator prints the routines it could not translate.
- The generated files are formatted by `cargo fmt`; regenerate them after a transpiler change and check `git diff`.
