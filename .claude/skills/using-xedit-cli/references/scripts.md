## Scripts

The Pascal scripts of the scripts folder, the corpus phase 6's interpreter parses and runs (xEdit's "Apply Script"). `script list` and `script check` need no `--game` or `--load`; `script run` loads the plugins it runs over, and `script resume` re-invokes a run that stopped on a dialog (issue #26's interaction bridge).

`xedit script check <file>...` compiles the given scripts and the units they `uses` with the JvInterpreter front end (phase 6 step 2, `crates/xedit-script`): as `TJvInterpreterUnit.Compile` does, a routine body is only scanned for its balanced `end`, so a statement-level error surfaces when the script runs, not here; unresolved identifiers belong to `script run`.

The units a script uses resolve from the scripts folder; a unit with no file there is a unit compiled into xEdit and parses to nothing.

It is read-only, exits non-zero when a script does not compile, and prints each failure as `file:line: message` (with `--json`, the structured result).

`xedit script run <file>` is xEdit's `-script:` mode (phase 6 step 4): the script compiles, `Initialize` runs, `Process` runs once per selected element, `Finalize` runs, and every plugin the run changed is saved (the `SaveChanged` of an auto mode) unless `--no-save` or `--dry-run`.

A routine that is missing, or that `FunctionIsEmpty` reads as `begin end` / `begin Result := 0; end`, is skipped; a non-zero result stops the run with `Script terminated itself, Result=<n>`; a failure prints the interpreter's `Exception in unit <u> line <n>: [<class>] <message>` and `Aborted: Applying script "<name>"`, exits non-zero, and still saves the plugins the run changed before the failure (the one-shot run stands in for the GUI's close, which saves them too; `--dry-run` and `--no-save` change nothing).

The message log goes to stdout (the `[mm:ss]` prefixes included, as xEdit's log has them); with `--json` it is `messages` in the response.

Since issue #26 the `Vcl` seam is the headless VCL object model (`crates/xedit-session/src/script_vcl/interactive.rs`): a script builds real form and control objects (assigning `X.OnClick := Handler` stores the routine; a button whose `ModalResult` is set closes a modal form, the VCL's own click rule) and a dialog it shows — `MessageDlg`, `InputQuery`/`InputBox`, `MessageBox`, `TOpenDialog`/`TSaveDialog`, a form's `ShowModal` — is answered from recorded inputs instead of a window.

Pass them with `--answer '<JSON>'` (repeat, in dialog order) or `--answers <file>` (a JSON array); each is `{"class", "title", "keys": [...], "button", "text", "control", "repeat"}` and matches a dialog by window class and caption substring, exactly as the parity harness answers the oracle GUI (`control` names the child control the text and keys go to, `repeat` a further answer to the same form, so a form with several controls is driven control by control; a file dialog's relative `text` is taken under its `InitialDir`).

Without an answer for a dialog the run stops and the response carries the question as `pending_interaction` (the question names its `kind`, `class`, `title`, `text` and `buttons`); append the answer and re-invoke with `script resume` (or `script run` again) — the interpreter has no continuation, so the script runs from its start with the answers supplied so far and proceeds past the interaction. `xedit schema` documents both requests.

Presentational members (`TCanvas` drawing and the paint methods) keep their state and draw nothing headless, and an assigned event handler is stored but not fired (a real message loop does that in the GUI).

| CLI | Registry name | What it does |
|---|---|---|
| `script list [--scripts DIR]` | `script.list` | Every `*.pas` of the scripts folder with its line count, as xEdit's script list shows them (the form's `_newscript_.pas` template included). The folder is `--scripts`, else `XEDIT_SCRIPTS`, else the oracle's `Edit Scripts` (`XEDIT_ORACLE_DIR`), else `Edit Scripts` beside `xedit.exe` (upstream's `wbScriptsPath`, which `-S:` sets); only the top folder is read. Read-only; error code `io` when the folder cannot be read. |
| `script check <file>...` | `script.check` | Compiles each script and the units it uses; the response has `ok`, `scripts_folder`, `total`, `parsed`, `failed` and per file `ok` with `errors` (`file`, `line`, `message`). |
| `script run <file> [--scripts DIR] [--no-save] [--dry-run] [--build-refs] [--answer JSON]... [--answers FILE]` | `script.run` | Runs the script over the loaded plugins (`--game`, `--load`), as `DoRunScript`/`ApplyScript` do. `--scripts` is the folder a relative script name resolves against (the units a script `uses` always read from the script's own folder, as `DoRunScript` sets `wbScriptsPath`). `--no-save` leaves the changed plugins in memory for `xedit save`; by default they are saved in place with the GUI's save log lines (`Saving: <name>.save.<time>`, `Queued renaming of save ... on shutdown.`, `Done saving.`) and without a backup folder. `--dry-run` runs the script with editing disabled and saves nothing. `--build-refs` builds the reference information first, as the GUI's script mode does at load (needed by scripts that read `ReferencedBy`). `--answer`/`--answers` supply the recorded dialog answers (issue #26). Needs `--edit` unless `--dry-run`. Response: `file`, `script` (the unit name), `dry_run`, `processed` (the elements `Process` ran on), `aborted`, `self_terminated` (the result that stopped the run), `error` and `error_location` of a failure, `files` (changed/saved, as `tool.run` reports them), `pending_interaction` (the dialog the run stopped on, when the answers ran out) and `messages`. |
| `script resume <file> [same options as run]` | `script.resume` | Continues a run that stopped on a dialog: the same request as `script run` with the accumulated answers. The interpreter has no continuation, so the script runs from its start again with the answers supplied so far; a deterministic script reaches the same state and proceeds past the interaction. |

- The selection of a run is the navigation tree walk of `DoRunScript`: every loaded file, and within a file every element from the last back to the file node, so a file's records are processed in the reverse of their order (the file header last) and the files in load order. `ScriptProcessElements := [etFile]` selects the file nodes; `ScriptProcessSignatures := 'WEAP,ARMO'` the records of those signatures (upper-cased and matched as a substring, as upstream).
- The script variables a script may set are those of `xejviScriptHost.pas`: `ScriptProcessElements`, `ScriptProcessSignatures`, `wbOutputPath`, `dfFloatDecimalDigits` and the filter fields (`FilterByName`, `FilterName`, `FilterConflictAllSet`, ...). Setting one the host does not know is xEdit's undeclared identifier.
- The script API is bound (phase 6 steps 5 to 9 and parity #25; `cargo xtask check` counts 3,663 `[script.*]` ledger entries, none pending): every host function of `xejviScriptAdapterHost.pas` (the message log, the loaded files, the paths, the filter, the load options, `wbSettings`, `wbRecordDefMap`, the file and record lookups, `AddNewFile`/`AddNewFileName`/`AddRequiredElementMasters` with their dialogs from the recorded answers, `IsPositionChanged`, the conflict helpers, `JumpTo` and the selection, `ExecuteCaptureConsoleOutput`, the LOD and atlas builders and the form handles `frmMain`/`frmFileSelect`, `crates/xedit-session/src/script_host.rs`), the `external` functions a script declares (called in their library), plus `Name`, `GetFileName`, `MasterCount` and `MasterByIndex`), the element, record, file, container and resource units (`crates/xedit-session/src/script_units/`), the data format surface (`script_df.rs`: the `TdfDef`/`TdfElement` classes over the NIF, material, LOD, FUZ and DDS code -- `ToText`/`ToJSON`/`FromJSON`/`SaveToFile`, `LoadFromResource` through the container handler), the misc family (`script_misc*.rs`, `script_strings.rs`, `script_classes.rs`: the `TStringList`/`TStrings`/`TEncoding` objects, the StrUtils/SysUtils/Math/Variants/WinAPI helpers, `wbFilterStrings`, `wbRemoveDuplicateStrings`, `GetRecordDefNames`, `FullPathToFilename`, `wbVersionNumber`, `Assigned`, `ObjectToElement`, `TwbVector`/`TwbGridCell`, `TPerlRegEx` and the `JsonDataObjects` surface with `Parse`/`ToJSON`/`LoadFromFile` and the `S`/`I`/`F`/`B`/`A`/`O`/`V` accessors), the JVCL RTL (`script_rtl/`: `System`, `SysUtils` -- `IntToStr`, `Format`, `Pos` -- , `Math`, the `Classes` unit's `TStringList`/`TList`/the `TStream` family, `JvInterpreterFm`'s four registrations through the `Vcl` seam), and the VCL surface (`script_vcl/`).

Every class, constant, property, method and helper a form script names is registered, so it compiles and runs; since issue #26 the seam's headless implementation is the VCL object model (`crates/xedit-session/src/script_vcl/interactive.rs`), which answers the forms, controls, properties and stored event assignments and takes its dialogs from the recorded `answers` (see "Scripts"); the four `JvInterpreterFm` form-runner functions still refuse with the `[EVclUnavailable]` text. `cargo xtask parity script` classes those corpus scripts `form`/`interactive`.

What answers headless: the `Windows` records (`TPoint`/`TRect`, `Point`/`Rect`/`Bounds`, `TopLeft`/`BottomRight`, the `MB_*`/`VK_*` constants), the `Controls` hint and cursor helpers, `IsAccel`, `KeysToShiftState`/`KeyDataToShiftState`, the `Menus` shortcut codec and the `IniFiles` classes with the `IOUtils` `TDirectory`/`TFile` helpers.

The ledger's `pending` and `excluded` notes are the authority on what a script can call; the `writing-xedit-scripts` skill covers writing one and its known divergences.
- `ApplyFilter` runs when the call that asked for it returns (the adapter functions do not hold the session the filter application needs), so the filter's own log lines appear after the current call's messages; `FilterApplied` answers true from the moment `ApplyFilter` is called, as upstream.
- With `FilterScripted` on, the filter calls the script's own `Filter(e: IInterface): Boolean` through the run's interpreter for every main record node its walk reaches (the same code path in one-shot, batch, serve and MCP sessions), and `Boolean(...)` reads its result: unassigned and 0 are False, a non-Boolean that does not convert raises `EVariantTypeCastError`.

The flag is read before every record, so a `Filter` function that clears it stops the scripted checks there, and the filter clears it when it ends.

A `Filter` function that raises aborts the run with `Error during Applying Filter: <message>`, the exception line and `Aborted:` -- no `Done: Applying Filter` line, and the messages of the statements after the `ApplyFilter` call are dropped (upstream aborts inside the call; the port applies a deferred filter when the call returns).

After the filter the `Process` walk sees only the nodes the filter kept (`ApplyScriptToSelection` walks the filtered tree); `RemoveFilter` returns the walk to every node.
- The `-script:<file>` switch and the `tmScript` mode (`xedit tool run script --script <file>`) run the same path; the legacy form saves the changed plugins, as the auto modes do.
- Error codes: `io` (the script is not there: `Could not open script: <path>`), `edit_required` (without `--edit`), `invalid_params`. A script that does not compile answers `aborted` with the interpreter's message and empty `messages`, since the run never started.
- The corpus is `crates/xtask/oracle/scripts/corpus.json`: the 150 scripts of the 4.1.5q `Edit Scripts`, 32 of which build a form and 11 ask the user for input (110 headless), with `xEditAPI.pas` the declaration-only API the scripts `uses`. The run cases of `cargo xtask parity script` are `crates/xtask/oracle/scripts/runs.json` (the 109 headless scripts and the 8 that ask for input); the `checking-parity` skill covers the harness, and the `writing-xedit-scripts` skill covers writing a script.
