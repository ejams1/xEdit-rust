## Quirks found and reproduced

- **JSON reads.** `FromJSON` reads values with the `JsonDataObjects` properties: `S[Name]` of an array or an object fails with `Cannot cast Array into String` (or `Object`), `O[Name]` and `A[Name]` add an empty object or array when the key is missing, `null` is a nil object (no struct, and `Cannot cast Object into Array` for an array), a repeated key keeps its first value, and a number reads as `Integer`, `Long`, `ULong` or `Float` as the library parses it.

A Fallout 4 `BSConnectPoint::Children` dump has an array `Name` where `NiExtraData` has its value `Name` (the array replaced the value when it was written), so xEdit cannot build that NIF from its own dump, and neither does the port.
- **Sine and cosine.** Delphi's `Sin` and `Cos` on Win64 are the RTL's own (an argument reduction with a three-part π/2 and two polynomial kernels), not the C runtime's and not correctly rounded: an ulp apart from either at times, which flips the sign or the last bit of a matrix element near zero after `AxisAngleToM33` (90 degree rotations, `Sin(Pi / 4)`). `nif_math::sin` and `nif_math::cos` are ported from the machine code of `Sniff.exe` (`System.Sin` at `0x40BDC0`, `System.Cos` at `0x40BCD0`, the reduction at `0x40B750`, the kernels at `0x40BB40` and `0x40BC10`) and give the bits that the GUI's script adapter returns for 20097 arguments. `ArcTan`, `ArcTan2`, `ArcCos` and `ArcSin` are the RTL's own too (`System.Math.ArcTan2` at `0x4717F0`, the polynomial at `0x40C390`); the Sniff tangent processor found it (the `Bitangent` bytes of Oblivion meshes), and they are ported in `nif_math` since phase 5 step 4. `StrToFloat` is the RTL's own as well: the digits accumulate into a `Double` (`value := value * 10 + digit`), the fraction digits count against the exponent, and the scaling is the same paired-table `Power10` that `FloatToDecimal` uses — `xedit_core::delphi::str_to_float` is that algorithm, fitted byte for byte against the oracle (`probes/numerics-parse.pas`, issue #39): the text of the largest double gives the double one ulp below `MaxDouble`, the 21 digits of Pi give `0x1.921fb54442d17p+1` where Rust's correctly rounded parse gives `...d18`, and the `Inf`/`Infinity`/`NaN` words parse (what `TextToFloat` reads before `Val` runs).

A malformed text and a value the scale sends to zero or infinity raise `EConvertError '<text>' is not a valid floating point value`.
- **Delphi number semantics in Sniff.** `SameValue` of two doubles uses a resolution of `1E-12` (the RTL's `DoubleResolution`, `Max(Min(|A|, |B|) * 1E-12, 1E-12)`); `xedit_core::delphi::same_value` is that function since parity #39 (the record code's `1E-15` was wrong for every site) and `nif_math` re-exports it.

Single expressions on Win64 are worked out in double precision and rounded when stored. `Round` of a NaN gives `-9223372036854775808` (the integer indefinite, as the floating point exceptions are masked), which the byte float setter then refuses with `'-9223372036854775808' is not a valid integer value`; `xedit_core::delphi::round` and `delphi::trunc` give the indefinite for a NaN or an out-of-range value since parity #39, where the script `Round`/`Trunc` keep the low 32 bits of the `Int64` (`Round(NaN)` is 0, `Round(1e19)` is 0) and `Ceil`/`Floor` are `Trunc` plus `Inc`/`Dec` on `Frac` (`Ceil(1e10+0.5)` is 1410065409): a Fallout 4 mesh with a NaN bitangent fails that way in `Apply transform`. `FloatToStrF` scales the value by the RTL's `Power10`, which multiplies by powers of ten held as pairs of doubles (high 26 bits and the rest) and by reciprocal tables for negative powers: `xedit_core::delphi::power10` is ported from `System.Power10` of `Sniff.exe` (0x40CDF0) since phase 5 step 4, which turned `0.000014 * 0.75` into `0.000011` as the oracle writes it (single double multiplications gave `0.000010`).

A probe through the script adapter is the way to read such a function: print each double as its exponent and two 26-bit halves of its mantissa, which the script computes exactly.
- **Name hashes.** The data format units find an element by comparing `dfCalcHash` of the names only (`HashName` of the ANSI string): each character in lower case is xored into the sum, which is then rotated left by five bits. `parity nif --text` compares it on the 1596 element names of the definitions.

The ASCII fold matches the oracle byte for byte (parity #39 probed every byte and name); the non-ASCII part is owed: the oracle's `dfCalcHash(Chr(160))`..`dfCalcHash(Chr(255))` is 65533 for every one of them and `Chr(128)`..`Chr(159)` is 2016 (the `?` of a character the code page cannot map) except at the five undefined CP1252 bytes (129, 141, 143, 144, 157), which are 65533 too, while the port's ANSI conversion plus ASCII fold gives the `rotl5` of the byte; the mechanism behind that constant was not solved (probes/numerics.pas records the table and docs/PLAN.md carries it as owed).

- **Float rounding.** `xDump.exe` 4.1.5q binds `IntPower(10, ADigit)` in `RoundToEx` to the `Single` overload, so a value is divided by and multiplied with the single-precision `10^-digits` in double precision, and 64-bit `FloatToDecimal` scales the result by a power of ten in double precision into an 18 digit mantissa before rounding to the decimals. `delphi.rs` reproduces both (`int_power_single`, `round_to_ex`, `float_to_decimal`). `make_float_probe.py <out.esp>` writes a plugin of 1800 GMST floats to probe the oracle (`xDump.exe -SSE -q -D:<dir> <out.esp>`), and `angle_probe.py <plugin> <oracle dump>` pairs the oracle's REFR rotation lines with the raw radians; both agree with the port.

Upstream's `TwoPi` is `2 * Single(3.1415927)` (`TWO_PI` in `constructors.rs`).

The rounding helpers were found by disassembling `xDump.exe` with `capstone`: `RoundToEx` loads `10.0` as a single before calling `IntPower`, and `Round` is a plain `cvtsd2si`.

The printing surface at full precision is probed by `probes/numerics.pas` (issue #39): `FloatToStrF(value, ffExponent, precision, digits)` has exactly `precision` significant digits from `FloatToDecimal` and pads the exponent to `digits` places only when `digits` is at most 4, so `FloatToStrF(1e22, ffExponent, 17, 0)` is `1.0000000000000000E+22` and `0.1` prints `1.0000000000000000E-1` where Rust's correctly rounded `{:e}` printed `1.0000000000000001E-001`.

Every operation of `FloatToDecimal` is an SSE operation in the `MXCSR` mode a script's `SetRoundMode` set (`xTESEdit.exe` 4.1.5q: `Power10` at `0xE4C0` changes only the precision mask, `Round` is `cvtsd2si` at `0xCB10`), so the digits depend on the mode (`0.3` is `2.9999999999999994E-1` under `rmDown`); the port replays each addition, product, quotient and rounding in the script's mode (`delphi::Arith`, the nearest result corrected by the sign of its exact error) and `sys-round.pas` compares the digits in all four modes. `TextToFloat` is the other way round: it sets the default control word (`SetMXCSR($1F80)`) around the parse, so a literal or a `StrToFloat` never follows the mode.
- **Length-prefixed strings read past their data.** `TwbLenStringDef.ToStringInternal` limits the text to the length of the whole data, prefix included, so a stored length larger than the data reads up to the prefix's bytes past the end of the element, out of the bytes that follow it in the file. A Fallout New Vegas save's dialogue `Response Text` showed it. `len_string.rs` reads those bytes from the block of the data container (`bytes_after` in `element.rs`).
- **Save tables keep elements, not values.** `InitializeSaveWorldspaceArray` stores the elements of the `Visited Worldspace` chapter and reads their values when a worldspace index is shown. Reading the values while the save loads resolved the names of the worldspace records before their strings were loaded, and the empty names stayed cached: a Fallout 4 save showed `<SanctuaryHillsWorld>` without its name.
