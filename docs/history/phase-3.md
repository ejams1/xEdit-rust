# Phase 3: Write path and daemon


- **Model:** Opus 5.5. Byte-identical saving and FormID and master rewriting are subtle but follow the upstream code closely.
- **Port:** Element editing, add and remove, copy as override and as new record, master management, FormID change and renumber, ESL/ESM/ESP flag handling, sort, save.
- **Performance:** Parse files in parallel with rayon, once the globals and the element initialisation are safe to share between threads (moved here from phase 1). Build and format records on worker threads for the dump (issue #4, item 3). Done in step 8; the threading model is below.
- **CLI:** `xedit elements set|add|remove`, `xedit records copy|delete`, `xedit masters add|clean|sort`, `xedit formids change|renumber`, `xedit files flags`, `xedit save`, `xedit batch`, all mutating ones with `--dry-run`. `xedit serve` keeps a session loaded and accepts the same commands as JSON-RPC. `xedit mcp` exposes the command registry as MCP tools generated from the schemas.
- **Skills:** `using-xedit-cli` version 2 with the mutation rules (edit flag, dry run, save, readback). `adding-a-command` (command, schema, CLI subcommand, test, ledger entry).
- **Gate:** Load then save is byte-identical for the corpus. A scripted edit sequence gives the same saved bytes as the oracle. Met 2026-10-07 for every plugin the oracle saves and for 3 of 4 edit sequences (see Status).
- **Steps** (one pull request, `phase-3-write-path`, #12; each step lands with its own check):
  1. **Round-trip save** (done): the modified states, `PrepareSave`, `WriteToStream`, the CRC32, `files.save` with `--dry-run` and the `--edit` gate, `cargo xtask parity roundtrip`.
  2. **Element editing** (done): the writeable storage of a record (`dcDataStorage`, `UpdateStorageFromElements`, `MergeStorage`), `SetEditValue`, `SetNativeValue` and `SetToDefault` for every definition type, every `AfterSet` and `AfterLoad` callback of the definitions, the required members added on init, the full `PrepareSave` (`HEDR`, `INCC`, `ONAM`, the flags that follow the extension, the FormID clamp), the record header read from `mrStruct`; `xedit elements set`, `xedit batch`.
  3. **Add, remove and copy** (done): `Add`, `Assign`, `RemoveElement`, `CopyInto` as override and as new record; `xedit elements add|remove`, `xedit records copy|delete`.
  4. **Masters** (done): `AddMaster`, `CleanMasters`, `SortMasters`, `MastersUpdated` with the FormID remap; `xedit masters add|clean|sort`.
  5. **FormIDs and flags** (done): `SetLoadOrderFormID`, renumbering, the ESL/ESM/ESP flag handling of `TwbFile`, `SortRecords`; `xedit formids change|renumber`, `xedit files flags`.
  6. **Oracle save** (done): the harness drives the oracle GUI build headlessly (its script mode, `-script:`, on private copies of the plugins) to produce the bytes xEdit saves, for the files the round trip cannot judge by the input alone (dropped `OFST` data, rebuilt `ONAM`, resorted groups, recompressed records) and for the scripted edit sequences of the gate; `cargo xtask parity oracle-save` and `cargo xtask parity oracle-edit`.
  7. **Daemon** (done): `xedit serve` (JSON-RPC over stdio and a named pipe) and `xedit mcp`.
  8. **Parallel loading** (done): files parsed with rayon, records built and formatted on worker threads for the dump (issue #4, item 3), once the globals are safe to share.
  9. **Skills and docs** (done): `using-xedit-cli` version 2, `adding-a-command`, README, ledger, map.
- **Threading model** (step 8, audit of every static, lock and lazily built table that loading and dumping touch; the code is `crates/xedit-core/src/threads.rs`):
  - *Immutable after setup:* the settings of `globals.rs` (atomics and `RwLock`s), the definitions and every table the definition units fill (`Global<T>` in `xedit-defs`, `RECORD_DEFS` and its index, the group order, the named indices, the record header and flag definitions, the FormID formaters, the contained-in definitions created once), the known subrecord signatures, the language encodings, the resource containers and the Starfield Wwise index.

They are written while a game is set up and loaded, before any parallel step.
  - *Per thread, as upstream's `threadvar`s:* the internal edit count and block (`_InternalEditCount`, `_BlockInternalEdit`), the resolve guard of an element (`esResolving`), and `PrecombinedCache`. The progress callback stays process-wide, so messages of worker threads reach stderr too, in no fixed order; stdout never carries them.
  - *Shared, with a lock:* the init of a container (`InitOnce`): another thread waits for a build in progress instead of seeing half of it, a build that needs a build of the waiting thread gives up and is counted (`init_cycles`; the dump then writes the affected batches again on one thread, with a warning; none seen on the corpus).

A main record is reset under the lock of its element list and read through `read_built`, so a reader that meets a reset builds the record again, and the released elements are dropped only once every line of the dump that began before the reset is done (`retire`, `ReadGuard`), so an element a line still holds keeps its links to its record.

The list of built records (`INITIALIZED_RECORDS`, trimmed with `try_lock`) and the pins of the records a worker writes.

The string tables (loaded once under a lock).

The FaceGen caches of the Fallout 4, Fallout 76 and Skyrim callbacks (built outside the lock, first one stored wins; the key is the race editor ID as upstream's, so two races with the same editor ID would make the cache depend on order, as it depends on the record order upstream).
  - *Parallel:* the scan of a plugin (`implementation/scan.rs`: groups from 128 KB on are read on the workers, the registration with the file and its masters is replayed on the calling thread in file order) and the dump (`ParallelDump`: the main records in batches of 512 on the workers, at most 4 batches at a time, written in file order).
  - *Serial only:* the load of a save (`TwbFileSource.Scan`) and the state the save definitions keep while one is read (the counters of `fo4saves`, the tables of `save_interface`, the flags of `fnvsaves`), `xedit saves dump`, and every session command (the edit paths read and change element lists directly and use the process-wide `wbCopyIsRunning`). A later parallel step must keep them on one thread or move that state into a context.

(7) *Harness.* An edit sequence with a FormID change needs the oracle's reference information (`build_refs`), which initialises every loaded record, so it runs only on a plugin whose records have no load fix-ups. (8) *Daemon.* A session is fixed at startup (no `session.load` command to switch plugins in a running daemon), the MCP server has no resources, prompts or progress notifications, and one named pipe client is served at a time because there is one session. (9) *Performance.* The registration of the scanned records (`AddMainRecord`, the light and update checks) is serial and the slowest part of a load; a session that loads several plugins loads them one after the other (each with its groups in parallel); the per-record caches that a build seeing another thread's partial build could fill (the precombined mesh, the FaceGen caches) are not reset when the dump writes a batch again after an init cycle (none was seen); the dump's speed-up is bounded by its slowest record per window of four batches (a Fallout 4 `RACE` takes 6 s).
